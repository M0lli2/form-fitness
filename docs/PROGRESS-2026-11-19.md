# Form 개발 진행 현황 — 2026-11-19

전체 완료율은 산정하지 않습니다. 요청한 '상위 앱의 모든 기능'의 고정된 목록·가중치가 없고 실기기 검증이 남아 있어 백분율은 오해를 만듭니다.

이 문서는 2026-11-19에 릴리스 주변을 정리한 유지보수 작업과, 그 작업이 확인한 상태만 적습니다. 새 기능 구현은 없습니다.

## 1. v0.2.0 릴리스에 Wear OS APK 추가

0.2.0 릴리스에는 휴대폰 APK 하나만 있었고 워치 동반 앱이 빠져 있었습니다. 같은 커밋 `c4452e4`의 v0.2.0 태그 빌드가 남긴 동반 앱 APK를 골라 릴리스에 추가했습니다.

워치 APK 후보는 세 가지였고, **휴대폰 APK와 서명이 같은지**로 골랐습니다.

| 후보 아티팩트 | 만든 실행 | 인증서 SHA-256 | 판정 |
|---|---|---|---|
| `form-wearos-debug` | [44476921135](https://github.com/M0lli2/form-fitness/actions/runs/44476921135) `wearos` 잡 | `df62fac39f8a9c49ce61a53262f65a6aa9e93bc93a7c598f499e4bf7d2f5852e` | 휴대폰과 불일치 — 제외 |
| `form-paired-wearos-debug` | [44476921135](https://github.com/M0lli2/form-fitness/actions/runs/44476921135) `android` 잡 | `fac61745dc0903786fb9ede62a962b399f7348f0bb6f899b8332667591033b9c` | 휴대폰과 일치 — **추가** |
| `form-paired-device-test-apks` 안의 워치 APK | [44476921197](https://github.com/M0lli2/form-fitness/actions/runs/44476921197) | `fac61745dc0903786fb9ede62a962b399f7348f0bb6f899b8332667591033b9c` | 같은 파일 계열(내용 동일) |

- `wearos` 잡은 자체 생성한 디버그 키스토어로 서명하므로 페어링 대상 휴대폰 앱과 인증서가 다릅니다. 페어링용 설치 파일로 쓸 수 없습니다.
- `android` 잡은 `-PformDebugKeystore`로 휴대폰 디버그 키스토어를 넘겨 워치 APK를 서명하고 `scripts/check-apk-pair.py`로 두 인증서 일치를 검사합니다. 그래서 이 아티팩트를 골랐습니다.

### 확인한 것

- 릴리스에 올린 뒤 **다시 내려받아** 해시를 대조했습니다. 로컬 파일과 같은 `d4371e9e…`, ZIP 168개 항목 손상 0.

- 두 APK의 서명 인증서 SHA-256이 `fac61745…`로 같습니다. 설치 화면·워치 페어링에서 서명 불일치로 막히는 경우는 이 조합에서 생기지 않습니다.

## 2. Android UI repack 회귀 실패의 원인

v0.2.0 태그의 `Android UI repack regression` [44476921059](https://github.com/M0lli2/form-fitness/actions/runs/44476921059)는 `prepare` 잡의 첫 단계에서 7초 만에 실패했습니다.

```
git diff --exit-code 54b42c6f… HEAD -- package.json package-lock.json app.json modules plugins
```

실패 로그의 diff는 `app.json` 한 파일이고, 내용은 `name` `FORM`→`Form`, `version` `0.1.0`→`0.2.0`, `ios.buildNumber` `2` 추가, `android.versionCode` `2` 추가입니다. 즉 **제품 결함이 아니라 0.2.0 릴리스 이전 커밋을 기준으로 잡아 둔 테스트 베이스라인 문제**입니다.

이 워크플로는 "기준 바이너리 대비 네이티브·구성 변경을 거부"하는 가드이고, repack에 넣는 휴대폰 APK는 별도 실행 [44209141146](https://github.com/M0lli2/form-fitness/actions/runs/44209141146)(커밋 `54b42c6`)의 `form-offline-release` 아티팩트입니다. 두 값이 같은 시점을 가리켜야 가드가 성립합니다.

## 3. 워크플로 수정안 — 적용 대기

`.github/workflows/android-repack.yml`의 기준을 0.2.0으로 올려야 합니다. **이 문서를 만든 작업에서는 그 파일을 커밋할 수 없었습니다.** 저장소에 연결된 토큰에 `workflows` 권한이 없어 `.github/workflows/` 아래 변경은 푸시가 거부됩니다(`refusing to allow a GitHub App to create or update workflow … without workflows permission`). 그래서 아래 diff를 남깁니다. GitHub 웹 편집에서 그대로 바꾸면 됩니다.

가드를 통과시키는 최소 변경은 한 줄입니다.

```diff
-      - run: git diff --exit-code 54b42c6f17143d84d084fa5c1e3819b02c0947cf HEAD -- package.json package-lock.json app.json modules plugins
+      - run: git diff --exit-code c4452e4792243e61ddb1dc84adc3ff63a904ca2c HEAD -- package.json package-lock.json app.json modules plugins
```

기준 바이너리와 기준 커밋을 같은 시점으로 맞추려면 같은 파일에서 두 줄을 더 바꿉니다. 0.2.0 커밋에서 성공한 `Android runtime smoke` [44476921003](https://github.com/M0lli2/form-fitness/actions/runs/44476921003)이 같은 이름의 `form-offline-release`(39,239,443 bytes, 만료 전)를 남겼습니다.

```diff
-          run-id: 44209141146
+          run-id: 44476921003
…
-          echo 'Base native commit: 54b42c6f17143d84d084fa5c1e3819b02c0947cf' > repack-evidence/provenance.txt
+          echo 'Base native commit: c4452e4792243e61ddb1dc84adc3ff63a904ca2c' > repack-evidence/provenance.txt
```

한 줄만 바꾸면 CI는 통과하지만, repack에 쓰는 APK는 여전히 0.1.0 시점(`54b42c6`) 바이너리라서 provenance가 말하는 기준과 실제 바이너리가 어긋납니다. 세 줄을 함께 바꾸는 쪽을 권합니다.

로컬 재현: 같은 명령을 저장소에서 돌려 `54b42c6` 기준은 exit 1, `c4452e4` 기준은 exit 0(차이 없음)을 확인했습니다. 기준만 바꿨을 때 가드가 통과한다는 뜻이고, 그 뒤 repack 단계(아티팩트 내려받기·빌드·에뮬레이터 여정)의 성공까지 보증하지는 않습니다.

검증 한계: 이 문서만 바꾼 커밋은 이 워크플로를 실행시키지 않습니다(트리거 경로는 `.github/workflows/android-repack.yml`과 `src/**`). 수정이 실제로 통과하는지는 워크플로 파일이 `main`에 반영된 뒤, 또는 수동 실행(`workflow_dispatch`)으로만 확인할 수 있습니다. 여기서 확인한 것은 (1) 현재 `main` HEAD가 `c4452e4`라 새 기준과 차이가 없다는 점, (2) `run-id` 44476921003의 아티팩트가 만료되지 않고 내려받힌다는 점입니다.

## 4. Dependabot 취약점 알림 — 권한 때문에 켜지 못함

`PUT /repos/M0lli2/form-fitness/vulnerability-alerts`는 403 `{"message":"Resource not accessible by integration"}`을 돌려줬습니다. 응답 헤더가 요구 권한을 `administration=write`로 표시합니다. 조회(`GET`)도 같은 403입니다. 저장소 메타데이터의 `security_and_analysis`는 여전히 `null`입니다.

저장소 Settings → Code security에서 직접 켜야 합니다. 켠 뒤에도 `npm audit`이 보고한 40개(높음 29·중간 11) 항목의 분류는 별도 작업입니다. `picomatch` GHSA-fc5q-39xc-vjpf는 확인 당시 수정 버전이 없었습니다([VALIDATION.md](VALIDATION.md) 기록). 이 환경에는 Node 도구가 없어 감사 결과를 다시 측정하지 않았고, 위 수치는 이전 기록 그대로입니다.

## 7. iOS 기능 동기화 (Android와 동일 기능으로)

"iOS 버전도 안드로이드 버전과 동일한 기능을 갖추게" 요청에 따라 `origin/main`(`ad435f5`)의 iOS/Android 차이를 전수 감사하고, 차이가 있던 iOS 동작을 고쳤다. 전체 감사표·파일별 변경·검증·남은 작업은 **[IOS-PARITY-2026-11-19.md](IOS-PARITY-2026-11-19.md)** 한 문서에 모았다(다른 도구로 이어서 작업할 수 있게 작성).
